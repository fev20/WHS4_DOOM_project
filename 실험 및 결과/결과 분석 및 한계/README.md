# 결과 분석 및 한계

## 결과 분석

홈캠의 펌웨어를 추출·분석하고 크로스컴파일한 DOOM을 실기기에서 실행해 브라우저로 보고 조작하는 데 성공했습니다.

DOOM은 화면·입력·파일·타이머를 모두 사용하기 때문에 이것이 동작했다는 것은 단순히 프로그램 하나를 올린 수준이 아니라 기기의 실행 환경 전반을 파악하고 제어했다는 것을 의미합니다. 특히 CGI가 빠진 제약 속에서도 기기에 이미 존재하던 웹서버 goahead와 함수를 재활용하여 외부 장비 없이 소프트웨어만으로 목표를 달성했다는 점에 의의가 있습니다.

## 한계

### 1. DOOM 화면 출력 경로의 제약

현재 DOOM 화면은 브라우저를 통해서만 볼 수 있습니다. 이 방식은 DOOM 픽셀 데이터 320×200을 WebSocket으로 브라우저에 전송해 자바스크립트로 렌더링하는 구조로, 카메라 본래의 영상 출력 경로인 센서에서 인코더를 거쳐 스트림으로 나가는 경로와는 무관한 별도 경로입니다.
[if it has a stream it can play doom](https://www.reddit.com/r/itrunsdoom/comments/1gjtcjs/if_it_has_a_stream_it_can_play_doom/)
이 프로젝트는 저희가 분석한 장치와는 다른 ipcam의 취약점을 통해 비디오 스트림 후킹을 통한 화면 출력을 진행한 프로젝트입니다.

이 프로젝트를 참고해 홈캠 앱에서 그대로 보이게 하는 방식도 구상했으나 시간 제약으로 해당 경로에 대한 분석 및 구현에는 착수하지 못했습니다.

### 2. Secure Boot 미적용 기기로 한정

이번 대상 기기는 Secure Boot가 적용되지 않아 펌웨어를 수정해 다시 올리는 방식이 가능했습니다. 만약 Secure Boot가 걸린 기기였다면 수정한 이미지가 부팅 단계에서 거부되므로 같은 접근을 그대로 적용할 수 없습니다.

참고로 본 프로젝트의 펌웨어 업데이트 과정에도 무결성 해시가 존재했으나 이는 펌웨어가 전송·저장 과정에서 손상되지 않았는지를 확인하는 수준의 검증으로 빌드 툴에서 해시를 재계산해 넣으면 통과할 수 있었습니다. 반면 Secure Boot는 부팅 시 제조사의 서명을 검증해 비인가 펌웨어를 거부하는 기능으로 서명 키가 없으면 해시를 재계산하더라도 통과할 수 없습니다. 따라서 둘은 서로 다른 층위의 검증이며 위 한계는 후자인 Secure Boot를 가리킵니다.

# 향후 연구 계획

## 1. 기존 홈캠 앱을 통한 DOOM 출력

현재는 브라우저로만 볼 수 있는 DOOM 화면을 기기 본래의 홈캠 앱에서 바로 볼 수 있게 하는 것을 목표로 합니다. 이를 위해서는 cam720과 통신하는 바이너리를 분석해 카메라의 비디오 스트림을 확인하고 이를 가로채는 방식으로 DOOM 화면을 cam720 앱에 출력하는 방식으로 계획중입니다.

## 2. 글리칭을 통한 Secure Boot 기기로의 확장

글리칭 기법으로 무결성 검증을 우회해 Secure Boot가 적용된 고가형 기기에서도 수정한 펌웨어를 실행시킬 수 있도록 하는 것을 목표로 합니다.

고가형 기기는 Secure Boot로 인해 수정 펌웨어가 부팅 단계에서 거부되므로 전압이나 클럭에 순간적으로 결함을 주입해 서명 검증 과정을 실패·우회시키는 방식을 연구합니다.
