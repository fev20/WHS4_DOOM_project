# 둠 트리거 구현

트리거는 프로그램을 실행하게 만드는 계기입니다. 여기서는 카메라에서 DOOM을 시작하는 방법을 다룹니다. 부팅 스크립트에 실행 명령을 넣는 방법과 웹 페이지의 버튼으로 실행하는 방법으로 나눕니다.

## 1. 부팅 스크립트에 DOOM 실행 명령 포함하기

카메라를 켤 때 DOOM도 자동으로 실행하려면 `/etc/init.d/rcS`에 실행 명령을 추가할 수 있습니다. `rcS`는 부팅 중 필요한 설정과 프로그램을 실행하는 스크립트입니다.

먼저 SD 카드에 DOOM 바이너리와 WAD 파일을 넣고, 바이너리에 실행 권한을 부여합니다. 아래 예시는 파일이 각각 `/mnt/sd_card/doomgeneric_camera`와 `/mnt/sd_card/doom.wad`에 있는 경우입니다.

```sh
chmod +x /mnt/sd_card/doomgeneric_camera
```

펌웨어를 풀어 놓은 폴더의 `etc/init.d/rcS`를 열어, 기존 초기화 코드 뒤에 다음 내용을 추가합니다. 아래 예시는 SD 카드의 파일이 준비될 때까지 기다린 다음 DOOM을 실행합니다.

```sh
# SD 카드의 DOOM 파일이 준비되면 자동 실행
(
    while [ ! -x /mnt/sd_card/doomgeneric_camera ] || [ ! -r /mnt/sd_card/doom.wad ]; do
        sleep 1
    done
    /mnt/sd_card/doomgeneric_camera -iwad /mnt/sd_card/doom.wad
) &
```

`-x`는 실행 파일에 실행 권한이 있는지, `-r`은 WAD 파일을 읽을 수 있는지 확인합니다. 파일이 아직 준비되지 않았으면 `sleep 1`로 1초 기다린 뒤 다시 확인합니다. 바이너리와 WAD 이름은 실제 사용하는 파일에 맞춰 바꿉니다.

`-iwad`는 사용할 WAD 파일을 지정하는 인자입니다. 바이너리와 WAD 모두 절대경로로 지정하므로, 부팅 스크립트가 어느 폴더에서 실행되든 같은 파일을 찾습니다. 추가 인자는 사용하는 바이너리에 맞게 지정합니다.

괄호 안의 작업 전체를 `&`로 백그라운드에서 실행하므로, SD 카드를 기다리는 동안에도 나머지 부팅 작업은 계속됩니다. SD 카드가 없거나 파일 경로·권한이 맞지 않으면 DOOM은 실행되지 않고 계속 기다립니다.

수정한 펌웨어를 적용한 뒤 재부팅하면 이 코드가 실행됩니다. 이 방식은 게임 프로세스를 자동으로 시작하며, PC 브라우저에서 게임 페이지를 여는 동작은 별도로 필요합니다. 실제 사용할 바이너리와 기기의 SD 카드 준비 순서에 맞춰 동작을 확인해야 합니다.

## 2. GoActions를 수정해 웹 버튼으로 DOOM 실행하기

카메라의 웹 로그인 화면에서 리셋 버튼을 누르면 DOOM이 실행되고 게임 화면으로 이동하도록 구성합니다. 여기서 리셋 버튼은 카메라 본체의 물리 버튼이 아니라 웹 페이지에 있는 버튼입니다.

카메라에는 웹 페이지를 제공하는 `goahead`라는 프로그램이 있습니다. 이 프로그램의 GoActions 기능은 특정 주소로 요청이 들어오면 연결된 기능을 실행합니다. 여기서는 이미 등록되어 있는 `login` 액션을 수정해, `/action/login` 요청이 들어오면 DOOM을 실행하도록 바꿉니다.

**카메라 웹 페이지의 로그인과 GoActions의 `login` 액션은 서로 다른 경로입니다.** 패치 후에도 카메라 웹 페이지의 로그인은 동작했으며, 해당 페이지가 `/action/login`이 아닌 다른 경로를 사용하는 것을 확인했습니다. 따라서 이 구현은 웹 페이지의 로그인 기능을 교체하는 것이 아니라, 별도로 등록된 `login` 액션을 DOOM 실행에 재사용하는 방식입니다.

기존 액션 내부에는 사용자 이름과 비밀번호를 읽고 `websLoginUser`를 호출하는 인증 코드가 있었습니다. 다만 이 액션이 원래 카메라의 어떤 화면이나 기능에서 사용되었는지는 확인하지 않았습니다. DOOM 실행에는 이 원래 용도를 확정할 필요 없이, 해당 요청으로 수정한 함수가 호출되는지 확인하면 됩니다.

```text
웹 페이지에서 리셋 버튼 클릭
    → 카메라에 /action/login 요청 전송
    → DOOM 실행 명령이 담긴 파일 실행
    → 게임 화면으로 이동
```

### 2.1. 준비할 파일

수정 대상은 다음과 같습니다. 경로는 카메라 내부를 기준으로 합니다. 펌웨어를 풀어 놓은 폴더에서 작업한다면 해당 폴더 아래의 같은 경로를 찾으면 됩니다.

| 파일 | 역할 | 수정할 내용 |
|------|------|-------------|
| `goahead` | 웹 요청을 받아 처리하는 프로그램 | GoActions의 `login` 액션을 스크립트 호출로 교체 |
| `route.txt` | 요청 주소와 처리 기능을 연결하는 설정 파일 | 기존 설정으로 액션이 호출되지 않을 때만 확인 |
| `/etc/webs/trigger` | DOOM 실행 명령을 담는 스크립트 | 사용할 DOOM 바이너리와 WAD 파일에 맞게 실행 명령 구성 |
| `/etc/webs/js/login.js` | 웹 로그인 화면의 버튼 동작을 정하는 파일 | 리셋 버튼에 실행 요청과 화면 이동 연결 |

스크립트는 여러 명령을 파일에 적어 한 번에 실행할 수 있도록 만든 파일입니다. WAD는 DOOM에서 사용하는 맵과 그래픽 등의 게임 데이터 파일입니다. DOOM 바이너리와 WAD가 준비되어 있고, 기기에서 직접 실행되는 상태를 기준으로 진행합니다.

### 2.2. 실행 요청을 받을 주소 확인하기

DOOM 실행에 사용할 주소는 `/action/login`입니다. **기존 설정으로 이 주소의 액션이 호출된다면 `route.txt`를 수정할 필요가 없습니다.** 패치 후 액션 호출 여부를 확인하는 방법은 2.4절에서 설명합니다.

아래 설정은 액션 요청이 연결되지 않을 때 확인할 항목입니다. 초기 QEMU 테스트에서는 이 설정을 추가하고 순서를 조정했지만, 모든 실행 환경에서 반드시 추가해야 하는 설정은 아닙니다.

```text
route uri=/action handler=action
```

이 설정은 `/action`으로 시작하는 요청을 웹 서버에 등록된 기능으로 전달하라는 뜻입니다. 추가해야 하는 경우에는 기존 `route uri=/` 줄보다 위에 둡니다. 아래에 넣으면 다른 설정이 요청을 먼저 받아 일반 파일을 찾게 될 수 있습니다.

### 2.3. GoActions의 login 액션을 DOOM 실행 기능으로 바꾸기

`goahead`는 사람이 읽는 소스 코드가 아니라 기계가 실행하는 파일입니다. 따라서 Ghidra로 파일을 열어 GoActions의 `login` 액션에 연결된 함수를 수정합니다. Ghidra는 실행 파일의 내부 명령을 확인하고 수정하는 도구입니다.

#### C 예제로 이식할 명령어 확인하기

MIPS 명령어를 처음부터 직접 작성하는 대신, 먼저 C로 `/etc/webs/trigger`를 실행하는 작은 프로그램을 만들었습니다. 이를 카메라의 CPU에 맞게 컴파일한 뒤 Ghidra에서 열어, `system` 호출이 실제로 어떤 명령어로 구성되는지 확인했습니다.

아래는 같은 동작을 하는 최소 예제입니다. `trigger_test.c`라는 파일로 저장합니다.

```c
#include <stdlib.h>

void script(void) {
    system("/etc/webs/trigger");
}

int main(void) {
    script();
    return 0;
}
```

PC에서 카메라용 실행 파일을 만드는 것을 크로스컴파일이라고 합니다. 카메라에 맞는 MIPS little-endian용 컴파일러인 `mipsel-linux-gcc`가 준비된 환경에서 다음처럼 컴파일합니다.

```bash
mipsel-linux-gcc -o trigger_test trigger_test.c
file trigger_test
```

`file` 결과에서 MIPS용 실행 파일인지 확인한 뒤, `trigger_test`를 Ghidra로 가져와 분석합니다. `script` 함수를 열면 디컴파일 창에서 `system("/etc/webs/trigger")` 호출을, Listing 창에서 그 호출을 수행하는 실제 MIPS 명령어를 볼 수 있습니다.

확인할 부분은 문자열 주소를 인자로 전달하는 명령, `system`의 주소를 가져와 호출하는 명령, 함수 시작과 끝에서 실행 상태를 저장하고 복원하는 명령입니다. 이 구조를 참고해 `goahead`의 `login` 액션에 이식했습니다.

테스트 프로그램의 바이트를 그대로 복사하지는 않습니다. 문자열의 위치와 `system`을 참조하는 위치는 실행 파일마다 다르므로, 호출 구조는 테스트 프로그램에서 확인하고 주소와 참조 값은 대상 `goahead`에 맞춰 설정합니다. 컴파일러와 옵션에 따라서도 명령어 배열이 달라질 수 있습니다.

#### 확인한 명령어를 login 액션에 이식하기

1. Ghidra에서 수정할 `goahead`를 열고 분석합니다.
2. `websDefineAction`에서 `login`이라는 이름에 연결된 함수를 찾습니다. 분석한 파일에서는 `FUN_0040f280`이었습니다.
3. 해당 함수가 로그인 처리 대신 `system`을 통해 `/etc/webs/trigger`를 실행하도록 명령어를 바꿉니다. `system`은 프로그램 안에서 셸 명령을 실행하는 함수입니다.
4. 함수 호출과 복귀에 필요한 상태 저장·복원 및 스택 처리를 넣습니다. 아래 패치에서는 복귀 주소인 `ra`를 저장했다가 복원합니다.
5. Ghidra의 `Patch Instruction`으로 명령어에 대응하는 바이트를 확인하고, 파이썬 스크립트로 실제 파일의 해당 부분에 적용합니다.
6. 변경된 파일을 다시 Ghidra에서 열어 수정 결과를 확인합니다.

수정할 명령어의 구성은 다음과 같습니다.

```text
기존 실행 상태 저장
    → /etc/webs/trigger 문자열의 주소 전달
    → system 호출
    → 기존 실행 상태 복원
    → 호출한 곳으로 복귀
```

이번 구현에 사용한 대상 파일의 값은 다음과 같습니다.

| 항목 | 확인한 값 |
|------|-----------|
| GoActions의 login 함수 범위 | `0x0040f280`~`0x0040f444` |
| 실행할 명령 문자열 | `/etc/webs/trigger` |
| system 주소를 가져오는 명령 | `lw t9,-0x7778(gp)` |
| system 호출 명령 | `jalr t9` |
| 함수 복귀 명령 | `jr ra` |
| 복귀 명령 다음 칸 | `nop` |

![기존 goahead에서 system을 호출하는 명령어](./img/image%201.png)

위 화면의 `lw t9,-0x7778(gp)`와 `jalr t9`가 기존 프로그램에서 `system`을 호출하는 부분입니다. 패치할 때도 이 프로그램이 사용하는 함수 주소를 기준으로 합니다.

`a0`는 실행할 명령 문자열의 주소를 전달하는 자리이고, `t9`는 호출할 함수의 주소를 담는 자리입니다. `nop`은 아무 작업도 하지 않는 명령입니다. 이 기기의 MIPS 명령 체계에서는 점프 바로 다음 명령도 실행되므로, 복귀 명령 뒤에 `nop`을 둡니다.

![Ghidra에서 확인한 login 액션 패치 결과](./img/image%202.png)

패치 결과를 확인한 화면입니다. 오른쪽에는 수정한 함수가 `system("/etc/webs/trigger")`를 실행하고 끝나는 것으로 표시됩니다. 왼쪽에는 이에 대응하는 기계 명령어가 보입니다.

실제 패치에 사용한 [파이썬 파일](./goahead_patch.py)의 명령어와 바이트는 다음과 같습니다. 사진에서는 `ra`의 저장·복원 위치가 `0x20(sp)`로 표시되지만, 아래 표는 파이썬 파일의 `0x2c(sp)`를 기준으로 작성했습니다. 바이트는 파일에 기록되는 순서대로 표기했습니다.

| 주소 | 명령어 | 바이트 |
|------|--------|--------|
| `0x0040f280` | `lui gp,0x6` | `06 00 1c 3c` |
| `0x0040f284` | `addiu gp,gp,-0x7530` | `d0 8a 9c 27` |
| `0x0040f288` | `addu gp,gp,t9` | `21 e0 99 03` |
| `0x0040f28c` | `addiu sp,sp,-0x30` | `d0 ff bd 27` |
| `0x0040f290` | `sw ra,0x2c(sp)` | `2c 00 bf af` |
| `0x0040f294` | `lui a0,0x40` | `40 00 04 3c` |
| `0x0040f298` | `ori a0,a0,0xf2b8` | `b8 f2 84 34` |
| `0x0040f29c` | `lw t9,-0x7778(gp)` | `88 88 99 8f` |
| `0x0040f2a0` | `jalr t9` | `09 f8 20 03` |
| `0x0040f2a4` | `nop` | `00 00 00 00` |
| `0x0040f2a8` | `lw ra,0x2c(sp)` | `2c 00 bf 8f` |
| `0x0040f2ac` | `addiu sp,sp,0x30` | `30 00 bd 27` |
| `0x0040f2b0` | `jr ra` | `08 00 e0 03` |
| `0x0040f2b4` | `nop` | `00 00 00 00` |

`0x0040f294`와 `0x0040f298`의 두 명령으로 실행할 문자열의 주소인 `0x0040f2b8`을 `a0`에 설정합니다.

`0x0040f2b8`에는 `/etc/webs/trigger` 문자열과 끝을 나타내는 `00`을 놓습니다. 문자열 전체를 바이트로 표현하면 다음과 같습니다.

```text
2f 65 74 63 2f 77 65 62 73 2f 74 72 69 67 67 65 72 00
```

끝의 `00`은 문자열의 끝을 나타냅니다. 문자열은 끝의 `00`을 포함해 18바이트이며, 뒤에 `00` 두 바이트를 더해 길이를 4바이트 단위로 맞춥니다. 그다음 `0x0040f2cc`부터 패치 영역 끝인 `0x0040f444` 직전까지를 `nop`으로 채웁니다. 명령어로서의 `nop`은 4바이트인 `00 00 00 00`입니다.

#### 파이썬 파일로 패치 적용하기

실제 파일에 바이트를 쓰는 작업은 [goahead_patch.py](./goahead_patch.py)로 진행했습니다.

수정 전 `goahead`와 `goahead_patch.py`를 같은 폴더에 두고, PC 터미널에서 그 폴더로 이동해 실행합니다.

```bash
python3 goahead_patch.py
chmod +x goahead_patched
```

입력 파일 이름은 `goahead`, 출력 파일 이름은 `goahead_patched`입니다. 원본은 덮어쓰지 않습니다. 다른 이름을 사용하려면 스크립트 맨 위의 `FIRMWARE_PATH`와 `OUTPUT_PATH`를 수정합니다.

스크립트는 명령어 56바이트, 정렬된 문자열 20바이트, NOP 376바이트를 합쳐 총 452바이트를 만듭니다. 문자열 주소가 명령어에 지정한 주소와 맞는지 확인하고, 실행 파일의 ELF 헤더를 읽어 패치할 파일 내 위치를 계산한 뒤 새 파일을 저장합니다. 완료 후 `goahead_patched`를 Ghidra에서 열어 위 명령어와 문자열이 반영되었는지 확인합니다.

이 스크립트는 위 주소와 함수 참조 값을 사용하는 바이너리를 대상으로 합니다. 다른 버전에도 같은 패치를 적용할 수 있는지 자동으로 판별하는 도구는 아닙니다.

위 주소는 프로그램 실행 시의 주소이며, 파일 맨 앞에서부터 센 위치와는 다릅니다. 파이썬으로 적용할 때는 실행 파일의 구조를 확인해 주소에 대응하는 파일 내 위치에 써야 합니다. 값은 이번에 사용한 `goahead` 기준이므로, 다른 버전에서는 함수 위치와 `system` 참조 위치를 다시 확인해야 합니다.

### 2.4. DOOM 실행 요청 확인하기

수정한 `login` 액션은 `/etc/webs/trigger`를 실행합니다. 이 파일에 아래 내용을 저장합니다. 예시는 SD 카드의 `/mnt/sd_card`에 `doomgeneric_camera`와 `doom.wad`를 넣은 경우입니다.

```sh
#!/bin/sh
/mnt/sd_card/doomgeneric_camera -iwad /mnt/sd_card/doom.wad &
```

| 부분 | 의미 |
|------|------|
| `#!/bin/sh` | 이 파일의 명령을 `/bin/sh`로 실행하도록 지정하는 첫 줄(셔뱅) |
| `/mnt/sd_card/doomgeneric_camera` | SD 카드에 넣은 DOOM 실행 파일의 절대경로 |
| `-iwad /mnt/sd_card/doom.wad` | 사용할 게임 데이터 파일을 절대경로로 지정하는 인자 |
| `&` | DOOM을 백그라운드로 실행하여 스크립트가 게임 종료를 기다리지 않고 끝나도록 지정 |

바이너리와 WAD 파일은 모두 `/`로 시작하는 **절대경로**로 지정합니다. 그래야 웹 서버가 어느 폴더에서 실행되든 같은 파일을 찾습니다. 바이너리의 이름이나 추가 인자가 다르면 실제 사용할 실행 명령에 맞게 바꿉니다.

이 파일들이 들어 있는 환경에서 스크립트와 DOOM 바이너리에 실행 권한을 부여합니다.

```sh
chmod +x /etc/webs/trigger /mnt/sd_card/doomgeneric_camera
```

PC에서 풀어 놓은 펌웨어로 테스트한다면, 위 절대경로는 chroot 안을 기준으로 합니다. SD 카드용 파일도 테스트 폴더의 `mnt/sd_card` 아래에 준비해야 합니다.

펌웨어를 풀어 놓은 `squashfs-root` 폴더에 들어가 QEMU로 실행을 확인했습니다. chroot는 풀어 놓은 폴더를 기기의 최상위 폴더처럼 사용하는 방법이고, QEMU는 PC에서 카메라용 프로그램을 실행하도록 돕는 도구입니다. 아래 명령은 이 환경이 준비된 상태에서 사용합니다.

PC 터미널에서 실행합니다.

```bash
sudo chroot ./squashfs-root /bin/sh
```

이어서 열린 셸에서 웹 서버를 실행합니다.

```sh
/usr/bin/qemu-mipsel-static -strace /bin/goahead /etc/webs 0.0.0.0:18081 &
```

PC의 브라우저 주소창에서 `http://localhost:18081/action/login`에 접속합니다. 확인할 결과는 웹 페이지의 표시 문구가 아니라 DOOM이 실제로 실행되는지입니다. 실행 추적 로그에 아래 내용이 나타나면 트리거 파일을 실행한 것입니다.

```text
execve("/bin/sh",{"/bin/sh","-c","/etc/webs/trigger",NULL})
```

여기에 DOOM 초기화 로그까지 출력되는지 확인합니다. 임시 BMP 화면 출력 경로인 `/tmp`에 게임 화면 파일이 생성되는 것도 확인했습니다. 게임이 실행되어도 브라우저에서 화면이 나오지 않으면 화면 파일을 제공하는 웹 서버 설정을 별도로 확인해야 합니다.

![action/login 요청 후 DOOM 초기화 로그와 BMP 파일 생성 확인](./img/image%203.png)

QEMU 테스트 화면입니다. 브라우저에서 `/action/login`에 접속한 뒤 오른쪽 터미널에 DOOM 초기화 로그가 출력되고, 왼쪽 파일 탐색기에 `doom.bmp`가 생성된 것을 확인할 수 있습니다.

![QEMU 환경에서 브라우저에 표시된 DOOM 화면](./img/image%204.png)

화면 제공 설정까지 적용한 뒤 브라우저에 게임 화면이 표시된 모습입니다. 이 사진은 PC의 QEMU 테스트 결과입니다.

### 2.5. 웹 페이지의 리셋 버튼 연결하기

`/etc/webs/js/login.js`를 열고 `$("#log_reset").click(...)` 부분을 찾습니다. 이 부분이 리셋 버튼을 눌렀을 때 실행되는 코드입니다. 버튼 동작에는 다음 두 기능을 연결합니다.

![웹 로그인 화면의 Reset 버튼과 개발자 도구의 요청 목록](./img/image%205.png)

수정할 버튼은 위 화면의 `Reset` 버튼입니다. 아래의 개발자 도구에서는 버튼을 눌렀을 때 요청이 전송되는지 확인할 수 있습니다. 이 사진은 패치 전 버튼 연결 테스트로, 표시된 `401` 응답은 DOOM 실행 성공을 뜻하지 않습니다.

1. `/action/login`으로 요청을 보내 DOOM을 실행합니다.
2. 게임 페이지인 `/doom.html`로 이동합니다.

요청을 보내는 코드와 페이지를 이동하는 코드는 각각 다음과 같습니다.

```javascript
$.get("/action/login");
```

```javascript
window.location.href = "/doom.html";
```

두 줄을 곧바로 연달아 실행하면 페이지 이동 때문에 실행 요청이 중단될 수 있습니다. 따라서 위 코드는 각 기능을 설명하기 위한 것으로, 완성된 버튼 코드는 아닙니다.

수정한 버튼 동작이 반영되지 않으면 브라우저에서 `Ctrl+Shift+R`을 눌러 강력 새로고침합니다. 이는 브라우저가 저장해 둔 이전 파일 대신 수정한 파일을 다시 읽도록 하는 방법입니다.
