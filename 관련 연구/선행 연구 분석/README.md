## 선행 연구 분석 이유
팀원들 모두 임베디드 기기를 대상으로 펌웨어를 추출하고 분석하거나 수정해 본 경험이 없거나 많지 않았기 때문에
프로젝트를 어떻게 진행해야 하는지 감을 잡기 쉽지 않았습니다. 

그래서 IoT 기기를 대상으로 펌웨어를 추출하고 분석을 하는 논문을 선행 연구로 선정하였습니다.

해당 연구에서 저희 팀원들은 평소 웹이나 일반적인 소프트웨어 프로젝트에서는 접하기 어려웠던 임베디드 기기의 펌웨어가 어떤 구조로 이루어져 있고,
실제 기기의 프로그램을 수정하기 위해서는 어떤 단계를 거처야 하는지 전체적인 흐름을 먼저 이해할 수 있었습니다.

## 선행 연구 분석

### Ⅲ. 제안 방법론 중 우리 프로젝트에 들어간 부분

**3.1 Firmware Extraction (펌웨어 추출)** <br>
**(1) Firmware Read**
1. 데이터시트 기반 SPI 핀 매핑표대로 칩 SPI 핀과 마이크로컨트롤러(라즈베리파이·아두이노) SPI 핀 연결
2. flashrom 오픈소스 툴로 칩 인식 후 펌웨어 이미지 덤프<br>
   flashrom은 수백 종의 플래시 칩·메인보드·프로그래머를 지원하며, 미등록 칩도 데이터시트를 바탕으로 직접 정보를 추가해 사용할 수 있습니다. PCB에서 칩을 떼지 않고 바로 읽는 것도 가능하나, PCB 노이즈로 인해 불완전한 덤프가 발생할 수 있어 Chip-Off 후 추출이 권장됩니다. <br>

**(2) File System Extraction**
binwalk로 덤프 이미지 내부의 파일시스템 시그니처를 탐지·추출합니다.
- binwalk: 파일시스템 및 데이터 구조 탐지·추출 기능 제공, 리패키징 기능 없어 별도 작업 필요
- firmware-mod-kit (fmk): 추출 시 fmk 디렉터리 생성·파일 수정과 재패키징을 함께 지원해 변조 작업에 용이 <br><br>


**3.2 Firmware Modify (셸 환경 활성화)** <br>
동적 디버깅을 위해서는 셸 환경이 필요하나 일반 사용자용 펌웨어는 기본적으로 비활성화되어 있습니다. 아래 3가지 변조 지점 중 파일시스템 상황에 맞는 방법을 선택합니다.
- 패턴 A. telnetd 활용: 파일시스템에 telnetd 바이너리가 있는 경우, 부팅 스크립트에 telnetd 실행을 추가하고 /etc/shadow를 수정해 telnet으로 root 접속
- 패턴 B. netcat 리버스 셸: nc 명령어가 있으나 네트워크 미연결 가능성이 있는 경우, 특정 서버로 지속 접속을 시도하는 리버스 셸 스크립트를 작성해 부팅 스크립트에서 백그라운드 실행
- 패턴 C. 명령어 정적 삽입: telnetd․nc가 모두 없는 경우, 기기 아키텍처(ARM/MIPS 등)를 확인 후 busybox․socat․nc를 정적 컴파일해 파일시스템에 삽입 (단, 용량 증가로 리패키징에 제약 가능성 존재)<br>
논문 실습 사례(JOOAN 카메라, 패턴 A): 부팅 스크립트에 「/usr/sbin/telnetd &」를 추가하고, /etc/shadow의 root 라인을 「root::10933:0:99999:7:::」 형태로 수정했습니다.

**(1) Firmware Repackaging** <br>
binwalk로 추출한 경우: 
- 파일시스템이 squashfs면 mksquashfs로 재패킹(원본과 동일 압축 알고리즘 사용), 그 외에는 mkfs.\[파일시스템타입\] 사용
- 재패킹된 이미지를 HxD 등 헥스 에디터로 원본 펌웨어의 해당 squashfs 오프셋 영역에 덮어쓰기
- 변조된 squashfs 크기가 다음 파티션 시작 오프셋을 초과하면 안 됨 (JOOAN 사례: 두 번째 squashfs가 0x418000부터 시작 → 첫 squashfs는 0x1b8000~0x260000 크기 이내로 제한)

firmware-mod-kit으로 추출한 경우:
- fmk/rootfs 디렉터리 내 파일을 직접 수정
- /firmware-mod-kit/build-firmware.sh 스크립트 실행, 전체 펌웨어 구조를 보존한 채 자동 리패키징 <br>

**(2) Firmware Write** <br>
Firmware Read와 동일한 SPI 연결 상태에서 flashrom으로 변조된 펌웨어 이미지를 칩에 재기록합니다. <br><br>

**3.5 Testing (검증)**
1. 전원 연결 후 정상 부팅 여부 확인
2. 변조 지점(telnet 등)이 정상 작동하는지 확인
3. (선택) SD카드 등에 대상 아키텍처용 gdbserver를 삽입, root 셸에서 실행 → 원격 GDB 연결로 본격적인 동적 분석 환경 구축 <br>
기기가 정상 부팅되지 않을 경우, 하드웨어 손상 또는 변조 과정의 오류일 수 있으므로 동일 모델의 정상 기기와 비교하여 원인을 규명해야 합니다.

### Ⅳ. 실전 적용 사례: JOOAN IP 카메라
- **Firmware Modify**: busybox 내 telnetd 활용 후 부팅스크립트에 telnetd 실행 추가, shadow 파일 수정
- **Repackaging/Write**: mksquashfs로 재패킹 후 HxD로 원본오프셋(0x1b8000~)에 덮어쓰기, flashrom으로 칩에 재기록
- **Rework/Testing**: telnet root 셸 획득에 성공, SD카드에 gdbserver를 삽입해 원격 디버깅 환경까지 구축

  
### Ⅴ. 방법론의 한계
- Secure Boot 적용 기기: 펌웨어 무결성 검증이 걸린 고가형 기기는 본 방법론만으로 셸 환경 구축이 불가하며, 글리칭 등 결함 주입(fault injection) 공격 기법과 결합해 확장할 필요가 있습니다.
- 다만 공유기·IP 카메라 등 소비자 노출도가 높은 대부분의 저가형 IoT 기기는 비용 문제로 Secure Boot를 적용하지 않는 경우가 많아, 실험을 통해 본 방법론의 실용성이 입증되었습니다.

### Ⅵ. 결론 및 시사점
본 논문은 SOP 타입 플래시 칩을 중심으로 IoT 기기의 펌웨어 추출과 동적 분석 환경 구축을 위한 체계적 방법론을 제시하고, 실기기(JOOAN IP 카메라) 적용을 통해 이를 검증했습니다. 범용성과 실용성을 갖춘 절차로 IoT 보안 연구자들의 분석 환경 구축 시간․비용 절감에 기여할 수 있습니다. 향후 과제로는 (1) Secure Boot 적용 고가형 기기로의 방법론 확장, (2) 펌웨어 변조 과정의 자동화가 제시됩니다.
